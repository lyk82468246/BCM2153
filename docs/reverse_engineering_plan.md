# BCM2153 逆向规划

目标：解释 GT-B5310U 固件的启动与解包、应用运行时、资源格式和文件系统之间的关系，逐步形成可复现的装载模型和接口说明。

本轮暂不研究蜂窝通信：GSM/UMTS 协议、注册入网、通话、短信、SIM/STK、射频及基带 DSP 均延后。`amss.bin` 只在涉及通用 RTOS、文件系统、USB 或应用主机依赖时按需查看，不以 AT 命令扫描作为主线。

## 执行顺序

### 第一轮：恢复证据状态，先做两个小闭环

1. REA 会话恢复后先检查 target、provider、analysis profile、已有快照和证据，避免重复建库。
2. 复用派生 ShpApp ELF，以 `0x0e00ad0c` 的 Thumb 入口为起点，只展开入口、初始化函数和相邻主机回调。记录 incoming `r0/r1`、`0x0e5e8c0c` 全局上下文、对象/表偏移、selector `0xb8` 和返回值用途；这些是待验证线索。
3. 对 `bcmboot.img` 追踪已知入口样代码 `0x28000030` 到 `bx 0x08400000`，分别画出加载成功和头部失败路径；重点检查 NAND 读取函数和实际写入目标缓冲区的代码。
4. 每条线都以一份短函数/数据流说明收尾，列出证据、假设和下一步缺口。此时不做全固件自动反编译。

建议首先执行第 2 步：已存在可解析的 ELF，能独立取得应用接口进展。第 3 步随后推进，服务于解包关键路径。

### 第二轮：打通启动与解包

- 从 bcmboot 的真实数据流判断 boot2 在何处、以何种布局被读取；检查文件头、页/块组织、复制、纠错处理或变换的可能性。
- “高熵”和“缺少标准魔数”不足以证明加密。必须定位读取/变换代码或可验证格式后，再实现针对性离线解码器。
- 对候选输出核对长度、`0xbabeface`、地址范围和多个代码路径，避免只凭一个匹配宣称解包成功。
- boot2 可分析后，追踪应用载入和 `apps_compressed.bin` 的块结构；若 boot2 仍不透明，继续 ShpApp/FactoryFs 的独立分析，记录阻塞边界。

交付：带坐标和证据来源的启动图、文件到 RAM 的映射表；若格式已确认，再交付离线解包脚本。

### 第三轮：应用模块与资源加载

- 搜索 FimBIN/ELF 加载、模块注册、主机表提供者和退出/卸载路径；在找到调用者前，不把 ShpApp 等同于全机 UI。
- 从已确认的主机回调和资源字符串向外展开，分别确认 Web/Widget、原生菜单、事件循环、显示和输入职责。
- IMRC 先按公开 Quram/Imaster 头模型验证块表和边界，再追踪读取代码。原始魔数扫描仅作为种子，资源边界必须由格式解析或已确认的长度字段支持。
- FactoryFs 优先检查 Widget 包、Java 描述文件、菜单/启动配置及挂载规则；按实际格式读取，不依靠目录名推断执行行为。
- Rsrc2 Low/Mid 暂列配置/profile 研究，不假设是完整资源银行，也不对其尾部字段直接命名为签名或校验和。

交付：应用模块图、主机 ABI 草图、资源 ID/文件路径到消费者的映射和残余未知项。

### 第四轮：评估最小复现

在前三轮证据基础上，选择一个与蜂窝无关的小行为，例如资源读取、Widget 初始化或输入事件处理，明确其状态和输出。先确定平台依赖，再选择局部仿真、接口桩或行为重建；此阶段不预设完整系统能在 QEMU 中直接启动。

真实设备 USB/UART 或 RAM 运行实验属于后续具体实验设计，不是本次粗略规划的完成条件。

## REA 路由和坐标约束

- 固件区域扫描使用 `inspect_firmware_regions`，先确认可用的 Binwalk provider；复用已有总览，只对具体缺口做补扫。签名候选不证明运行地址和资源长度。
- 原生代码使用 `open_binary` 后的函数分析、调用关系、字符串引用与局部 CFG。ARM/Thumb 上下文和函数边界需交叉验证，伪代码不视为原始源码。
- ShpApp 使用容器偏移 `0x192e` 的派生 ELF；先核验派生文件与父样本的关系并记录两者哈希。此前 ELF loader 选用 ARMv8 language 不代表目标 CPU 是 ARMv8，必须核实处理器设置。
- bcmboot 的映射为“父文件偏移 `0x40` → VMA `0x28000000`”。REA raw-binary 将偏移 0 映射到给定地址，不能直接把未裁剪文件设为 `0x28000000`。复用正确的 Ghidra 导入，或生成有来源记录的派生切片。实际入口种子与装载基址分别记录。
- `amss.bin` 的 `0x80300000` 仍保留为已有装载假设；仅在通用平台依赖需要时打开。
- 大结果使用 summary 和分页视图，保存完整 Evidence ID 与限制。导出本地 evidence bundle/可复用 snapshot 后关闭本轮打开的目标；具体能力以实际 provider 为准。
